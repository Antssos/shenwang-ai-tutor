# 申望 AI 助教前端 v0.1 技术方案

文档状态：折中架构已确定，待实施  
编写日期：2026-07-23  
适用阶段：内部联调与小范围试点  
产品名称：望学伴

## 1. 方案结论

v0.1 采用“Vercel 托管移动端 React Web + 阿里云运行安全代理（BFF）+ 服务器内网 Dify Chatflow”的折中方案。

```text
GitHub 私有仓库 ──自动部署──→ Vercel（React + Vite 前端）
                                      ↓ HTTPS / SSE
                              api.example.com
                                      ↓
                              Cloudflare Tunnel
                                      ↓
                    阿里云 127.0.0.1:3000（Hono BFF）
                                      ↓ 服务器内部访问
                              Dify 127.0.0.1/v1
                                      ↓
                            知识库 + 外部模型 API
```

核心原则：

1. 前端从 GitHub 自动部署到 Vercel，前端开发者不需要登录服务器发布页面。
2. 前端只调用团队自己的 BFF，绝不直接调用 Dify，也不保存任何 API Key。
3. BFF 与 Dify 继续运行在同一台阿里云服务器，Dify API 不直接暴露公网。
4. Cloudflare Tunnel 只把 BFF 的本地端口映射为 HTTPS API 域名，不映射 Dify 管理后台。
5. Dify 管理后台继续通过 SSH 隧道访问，不向普通用户开放。
6. v0.1 只做文字聊天；文件、图片、语音和小程序外壳暂不实现。
7. 默认不收集儿童姓名、手机号、住址、学校、照片等身份信息。
8. 高风险内容仍由 Dify 固定分支处理，前端只负责明确展示，不自行生成安全建议。

## 3. v0.1 范围

### 3.1 必须实现（P0）

- 手机和电脑均可使用的响应式聊天页面。
- 显示 Dify 开场白和三个入口提示：问学习、了解中心、说说心情。
- 文字提问与 SSE 流式回答。
- 同一页面内延续 `conversation_id`。
- 生成中停止回答。
- 新建对话及清除当前对话。
- 加载、断线、超时、限流、服务不可用和空答案提示。
- 安全风险固定回复使用醒目但不惊吓儿童的卡片展示。
- 基础隐私提示和“不输入个人信息”的提醒。
- 试点访问限制、请求限流、输入长度限制和日志脱敏。

### 3.2 建议实现（P1）

- 对回答点赞 / 点踩。
- 安全展示经过白名单处理的资料来源名称。
- 刷新页面后恢复当前会话消息。
- 后端健康状态提示。
- 低网速下的自动重连提示。

### 3.3 暂不实现

- 图片、文档、音频、视频上传。
- 语音输入和语音播放。
- 微信登录、儿童个人账号和个人画像。
- 长期保存聊天内容。
- Office 文件处理。
- 复杂动画、积分、排行和游戏化功能。
- 直接暴露 Dify WebApp 或 Dify API。

## 4. 技术选型

### 4.1 前端

| 项目 | 选择 | 原因 |
| --- | --- | --- |
| 框架 | React + TypeScript + Vite | 与现行方案一致，生态成熟，适合学生团队快速开发 |
| 前端托管 | Vercel + GitHub 集成 | 分支自动生成预览，合并 `main` 后自动发布正式版本 |
| 样式 | Tailwind CSS | 快速完成响应式设计，减少重复 CSS |
| 路由 | React Router | 支持聊天页、隐私说明页和关于页 |
| 状态 | React Hooks + `useReducer` | v0.1 状态量有限，暂不引入大型状态库 |
| 流式请求 | `fetch` + `ReadableStream` | Dify 聊天接口是 POST，不能直接使用浏览器 `EventSource` |
| Markdown | `react-markdown` + `remark-gfm` + `rehype-sanitize` | 展示列表、代码和公式说明，同时阻止危险 HTML |
| 数据校验 | Zod | 前后端共享请求和响应结构 |
| 单元测试 | Vitest + Testing Library | 验证状态机、SSE 解析和组件行为 |
| 端到端测试 | Playwright | 验证移动端聊天主流程和异常状态 |

Vercel 原生支持 Vite，因此使用 Vercel 并不要求改成 Next.js。当前页面以单页聊天为主，没有服务端渲染和复杂内容站需求，保留 Vite 能降低学习和排错成本。若主力前端开发者只熟悉 Next.js，可以在不改变 BFF 和 Dify 边界的前提下替换前端框架，但 v0.1 不使用 Next.js Route Handler 连接 Dify。

### 4.2 安全代理 BFF

建议使用 Hono + TypeScript，以 Node.js Docker 容器部署在当前阿里云服务器上。

原因：

- BFF 与 Dify 同机，可通过服务器内部地址访问 `/v1`，无需把 Dify API 暴露到公网。
- Hono 代码较轻，可在后续需要时迁移到 Cloudflare Worker。
- BFF 可以集中保存 Key、限流、脱敏、转换 SSE 事件和统一错误码。
- BFF 只监听服务器回环地址，由 Cloudflare Tunnel 提供 HTTPS 公网入口，不与当前 Dify 占用的 80 端口冲突。

Cloudflare 在本方案中只承担 DNS、HTTPS 和 Tunnel 入口，不承担 BFF 运算。这样流式请求不会受到 Vercel Function 的运行时长约束，Dify Key 也不需要上传到 Vercel。未来如果确实迁移到 Cloudflare Worker，再单独评估儿童数据链路、流式限制和服务器入口认证。

## 6. 页面与交互设计

### 6.1 页面结构

v0.1 包含三个路由：

| 路由 | 作用 |
| --- | --- |
| `/` | 聊天主页 |
| `/privacy` | 儿童友好的隐私说明 |
| `/about` | 能力范围、AI 声明和中心信息 |

聊天主页采用移动端单栏布局：

```text
┌────────────────────────────┐
│ 望学伴             新对话  │
│ AI 助手 · 服务状态          │
├────────────────────────────┤
│ 开场白                      │
│ [问学习] [了解中心] [说心情]│
│                            │
│ 用户消息                    │
│                助手流式回答 │
│                [停止回答]   │
├────────────────────────────┤
│ 请不要输入姓名、电话或住址  │
│ [输入问题……]         [发送] │
└────────────────────────────┘
```

### 6.2 视觉规则

- 整体温和、清晰，不使用医疗化、监控感或过度幼稚的视觉语言。
- 主色建议采用柔和蓝绿色，警示状态使用暖橙色，现实危险状态才使用少量红色。
- 正文字号不小于 16px；儿童主要阅读内容建议 17–18px。
- 所有可点击控件最小触控区域为 44×44px。
- 单行长度在桌面端控制在约 60–75 个中文字符内。
- 动画只用于流式光标和轻微状态切换，并支持 `prefers-reduced-motion`。
- 不使用“诊断结果”“心理治疗”等可能误导的词语。

### 6.3 开场与输入

首次进入显示：

> 你好，我是望学伴。你可以问学习问题，也可以了解申望儿童关爱服务中心。遇到让你害怕或不安全的事情，请先告诉身边可信任的大人。

输入框规则：

- 空内容不能发送。
- v0.1 建议最多 1,000 个中文字符。
- 发送后立即锁定重复提交，允许点击“停止回答”。
- 页面始终显示“请不要输入姓名、电话、住址、学校班级或照片”。
- 快捷问题只填入输入框，由用户再次确认发送，不自动提交。

### 6.4 消息展示

- 用户消息右侧，助手消息左侧。
- 流式文本逐段追加，不为每个字符触发复杂动画。
- Markdown 允许标题、段落、列表、加粗、表格和代码块。
- 禁止渲染原始 HTML、脚本、iframe 和不受信任的内联样式。
- 外部链接默认显示离站提示，并添加 `noopener noreferrer`。
- 知识库引用只展示经过 BFF 白名单处理的资料标题，不展示数据集 ID、服务器路径和完整检索片段。

### 6.5 安全风险状态

Dify 的高风险固定分支是安全底线，前端不得把它改写为普通聊天气泡。

推荐显示为独立卡片：

- 标题：“现在先找一位可信任的大人”。
- 原样展示 Dify 固定回复。
- 提供“新建对话”按钮。
- 不展示继续追问的推荐问题。
- 不自动给出未经项目方核验的电话号码、机构名称或医疗建议。
- 前端不承诺保密，不显示“只有我们知道”等文案。

BFF 可以根据 Dify 流中的安全节点事件转换出 `safety` 事件；即使前端识别失败，Dify 固定回复仍必须正常展示。

## 7. 前端状态机

```text
idle
  └─发送→ connecting
              ├─收到首段→ streaming
              │             ├─完成→ completed
              │             ├─停止→ stopped
              │             └─断线→ error
              ├─限流→ rate_limited
              ├─超时→ timeout
              └─服务异常→ unavailable
```

前端状态至少包含：

```ts
type ChatStatus =
  | 'idle'
  | 'connecting'
  | 'streaming'
  | 'completed'
  | 'stopped'
  | 'rate_limited'
  | 'timeout'
  | 'unavailable'
  | 'error'
```

每次请求保存：

- `requestId`：团队链路追踪 ID。
- `taskId`：Dify 任务 ID，用于停止生成。
- `messageId`：Dify 消息 ID，用于反馈。
- `conversationId`：Dify 会话 ID，用于延续和删除会话。

## 8. BFF 接口设计

前端只允许访问以下团队接口。接口统一使用 `/api/v1` 前缀。

### 8.1 获取安全配置

```http
GET /api/v1/config
```

只返回可公开字段：

```json
{
  "appName": "望学伴",
  "openingStatement": "你好，我是望学伴……",
  "suggestedQuestions": ["我有一道数学题不会", "中心有哪些活动？", "我今天有点难过"],
  "maxInputLength": 1000,
  "feedbackEnabled": false,
  "sourcesEnabled": true
}
```

不得返回 Dify 地址、API Key、模型供应商密钥或内部数据集 ID。

### 8.2 建立试点会话

```http
POST /api/v1/session
Content-Type: application/json
```

试点阶段可要求输入由老师分发的访问码。验证成功后，BFF 设置短期的 `HttpOnly + Secure + SameSite=Lax` Cookie。前端 JavaScript 不读取鉴权令牌。

### 8.3 发送聊天消息

```http
POST /api/v1/chat/stream
Content-Type: application/json
Accept: text/event-stream
```

请求：

```json
{
  "message": "五年级数学这道题应该怎么想？",
  "conversationId": "",
  "clientId": "随机匿名标识"
}
```

BFF 转换成 Dify 请求：

```json
{
  "inputs": {},
  "query": "五年级数学这道题应该怎么想？",
  "response_mode": "streaming",
  "conversation_id": "",
  "user": "经过服务端处理的匿名用户标识",
  "auto_generate_name": true
}
```

BFF 从环境变量读取：

```text
DIFY_API_BASE=<服务器内部 Dify /v1 地址>
DIFY_API_KEY=<专用于望学伴的 Service API Key>
```

### 8.4 团队 SSE 事件

BFF 不把所有 Dify 内部事件原样暴露给前端，而是转换成稳定契约：

```text
event: status
data: {"phase":"routing","requestId":"..."}

event: delta
data: {"text":"先看题目给了哪些条件……"}

event: safety
data: {"active":true}

event: done
data: {"taskId":"...","messageId":"...","conversationId":"...","sources":[]}

event: error
data: {"code":"UPSTREAM_UNAVAILABLE","message":"服务暂时不可用，请稍后再试"}
```

映射规则：

| Dify 事件 | BFF 行为 |
| --- | --- |
| `message` | 转换为 `delta` |
| `message_end` | 提取 ID、用量和安全来源后转换为 `done` |
| `message_replace` | 清空当前助手内容并用替换文本重新输出 |
| `workflow_started` / `node_started` | 可转换为不泄露节点细节的 `status` |
| `node_finished` | 只用于识别安全分支和后端观测，不把节点输入输出直接发给前端 |
| `ping` | 保活，不展示 |
| Dify 错误事件 | 转换为团队统一错误码 |

### 8.5 停止生成

```http
POST /api/v1/chat/{taskId}/stop
```

BFF 转发到 Dify：

```http
POST /chat-messages/{task_id}/stop
```

### 8.6 清除会话

```http
DELETE /api/v1/conversations/{conversationId}
```

BFF 转发到 Dify 会话删除接口，并清除浏览器中的当前 `conversationId`。界面上的“清除对话”必须说明该动作无法撤销。

### 8.7 反馈（P1）

```http
POST /api/v1/messages/{messageId}/feedback
```

仅允许 `like`、`dislike` 和可选的固定原因编号；不要让儿童在反馈框再次提交隐私内容。

## 9. 错误码约定

| HTTP | `code` | 前端文案 |
| --- | --- | --- |
| 400 | `INVALID_INPUT` | 请检查输入内容后再试 |
| 401 | `SESSION_REQUIRED` | 本次访问已过期，请重新进入 |
| 413 | `INPUT_TOO_LARGE` | 内容有点长，请缩短后再发送 |
| 429 | `RATE_LIMITED` | 提问太快了，请稍等一会儿 |
| 502 | `UPSTREAM_ERROR` | AI 服务暂时没有正常返回 |
| 503 | `SERVICE_UNAVAILABLE` | 服务正在休息，请稍后再试 |
| 504 | `UPSTREAM_TIMEOUT` | 回答时间较长，请重新试一次 |

错误响应只返回面向用户的安全信息和 `requestId`，不返回堆栈、Dify 原始错误、容器名或 Key。

## 10. 隐私与安全要求

### 10.1 前端

- 不保存 Dify Key、模型 Key、SSH 信息和服务器管理地址。
- 不把完整聊天内容写入 `localStorage`。
- 匿名 `clientId` 使用 `crypto.randomUUID()` 生成，不包含真实身份。
- 当前 `conversationId` 建议只放 `sessionStorage`；关闭标签页后失效。
- 所有模型输出经过 Markdown 消毒后显示。
- 不接收文件、照片和录音。
- 不在分析工具中上报完整问题或回答。

### 10.2 BFF

- 只允许正式前端域名访问，禁止 `Access-Control-Allow-Origin: *`。
- 限制请求体大小和输入长度。
- 单匿名用户同一时间最多一个生成任务。
- 建议初始限流：每分钟 10 次、每天 100 次；上线前根据试点规模调整。
- 上游连接建议首包超时 30 秒、总时长上限 120 秒。
- 日志只记录 `requestId`、匿名用户哈希、耗时、状态码、路由类别和用量，不记录完整问答。
- API Key 只存服务器环境变量或 Docker Secret，不写 Git、镜像和前端构建产物。
- 定期轮换 Dify Key；前端开发者不需要获得该 Key。
- 设置明确的数据保存期限，并提供会话删除能力。

### 10.3 试点访问控制

v0.1 不建议一开始完全公开。建议先使用“访问码 + HttpOnly 会话 Cookie”限制为内部试点用户，同时保留服务端限流。待内容审核、隐私说明、应急流程和成本监测完成后，再决定是否开放注册或公开访问。

## 11. 折中部署方案与操作流程

### 11.1 最终拓扑

推荐准备一个根域名，并划分两个子域名：

| 地址 | 承载位置 | 用途 |
| --- | --- | --- |
| `app.example.com` | Vercel | 用户访问的 React 页面 |
| `api.example.com` | Cloudflare Tunnel → 阿里云 | 前端唯一允许调用的 BFF |
| `127.0.0.1:3000` | 阿里云服务器 | BFF 容器，仅本机监听 |
| `127.0.0.1/v1` | 阿里云服务器 | Dify Service API，仅服务器内部访问 |
| `127.0.0.1:8080` | 管理员电脑 | 现有 SSH 隧道入口，只用于 Dify 后台管理 |

完整请求流程如下：

1. 用户打开 `app.example.com`，HTML、JavaScript 和样式由 Vercel 返回。
2. 前端请求 `api.example.com/api/v1/chat/stream`，并携带 BFF 签发的试点会话 Cookie。
3. Cloudflare 将 HTTPS 请求通过 Tunnel 转发到服务器 `127.0.0.1:3000`。
4. BFF 完成来源校验、会话校验、限流、输入检查和匿名用户映射。
5. BFF 使用服务器环境变量中的 Dify Key 请求内部 Dify `/v1/chat-messages`。
6. Dify 完成分类、知识库检索和外部模型调用，并返回 SSE 数据流。
7. BFF 清理内部节点信息，把 Dify 事件转换为团队事件，再经 Tunnel 流回浏览器。

这条链路中，Vercel 不接触 Dify Key，Cloudflare 不负责业务逻辑，浏览器不知道 Dify 地址。Dify 管理后台的 SSH 访问方式保持不变。

### 11.2 为什么选择 Cloudflare Tunnel

当前 Dify Nginx 已占用服务器 80 端口，而 BFF 还需要一个安全的 HTTPS 公网入口。若直接在服务器再配置一套公网 Nginx，需要调整 Dify 端口、申请证书并开放 80/443，操作风险较高。

Cloudflare Tunnel 由服务器主动向 Cloudflare 建立出站连接，再把 `api.example.com` 映射到 `http://localhost:3000`。它不要求为 BFF 新开公网入站端口，也不会改变现有 Dify 端口。正式环境使用受账号管理的命名 Tunnel；随机的 Quick Tunnel 只用于临时测试。

需要明确：Tunnel 解决的是安全接入和 HTTPS，不等于用户鉴权。只要知道 `api.example.com`，理论上就能发起请求，因此访问码会话、来源校验、限流和输入检查仍由 BFF 实现。

### 11.3 域名和账号准备

实施前需要准备：

1. 一个团队可长期控制的域名，不使用个人临时域名作为正式地址。
2. 将该域名接入 Cloudflare DNS，用于创建 `api` Tunnel 路由。
3. 一个 Vercel 项目，并授权读取当前 GitHub 私有仓库。
4. 一个专用于望学伴的 Dify Service API Key。
5. 明确三类负责人：GitHub/Vercel 负责人、服务器/BFF 负责人、Dify 负责人。

Vercel Hobby 适合个人、小规模和非商业试验，但多人私有仓库协作的自动部署可能受到提交者身份限制。试点开始前应实际验证朋友提交 PR、仓库所有者合并后是否能正常生成 Preview 和 Production 部署；若团队成员都需要独立触发部署，再评估 Pro，而不是默认承诺永久免费。

### 11.4 前端工程和 Vercel 环境

`web/` 继续使用 React + TypeScript + Vite。Vercel 项目的 Root Directory 指向 `web`，构建命令、输出目录和 Node 版本在 Vercel 项目设置中固定，不依赖开发者本机默认值。

Vercel 只需要保存可以公开的前端配置：

| 环境变量 | 示例含义 | 是否会进入浏览器 |
| --- | --- | --- |
| `VITE_API_BASE_URL` | `https://api.example.com` | 会，属于公开地址 |
| `VITE_APP_ENV` | `preview` 或 `production` | 会 |
| `VITE_FEEDBACK_ENABLED` | 是否显示反馈按钮 | 会 |

所有 `VITE_` 前缀变量都应视为公开信息。Dify Key、模型 Key、服务器地址、SSH 信息、访问码原文和 Cookie 签名密钥不得配置在 Vercel，也不得出现在 `web/`。

建议设置两类 Vercel 环境：

- Preview：每个分支或 PR 自动部署，默认连接 Mock API 或专用测试 BFF。
- Production：只有 `main` 分支部署，连接正式 `api.example.com`。

不要把所有动态 `*.vercel.app` 预览地址加入正式 BFF 的 CORS 白名单。否则任何未审核分支都可能调用正式儿童服务和消耗模型额度。确需真实联调的 Preview 地址，由服务器负责人短期加入精确白名单，测试结束后删除。

### 11.5 BFF 容器运行方式

BFF 使用独立的 `deploy/docker-compose.bff.yml` 管理，不修改、不重启 Dify 的 Compose 项目。建议形成单独镜像，并使用 Git 提交 SHA 作为镜像标签，避免只使用无法回溯的 `latest`。

BFF 容器应满足：

- 应用在容器内监听 3000。
- Docker 只发布到宿主机 `127.0.0.1:3000`，不发布到 `0.0.0.0`。
- 配置 `restart: unless-stopped`，服务器重启后自动恢复。
- 提供 `/healthz`，成功时只返回简单健康状态。
- 通过 `host.docker.internal:host-gateway` 访问宿主机上的 Dify Nginx。
- 不挂载知识库目录，不读取 Dify 数据库，不直接连接 Dify Redis。

建议的服务器环境变量：

| 变量 | 用途 |
| --- | --- |
| `DIFY_API_BASE` | BFF 可访问的内部 Dify `/v1` 地址 |
| `DIFY_API_KEY` | 望学伴专用 Dify Key |
| `ALLOWED_ORIGINS` | 精确的正式和临时联调前端地址 |
| `SESSION_SECRET` | 签发试点会话 Cookie |
| `PILOT_ACCESS_CODE_HASH` | 访问码哈希，不保存访问码明文 |
| `MAX_INPUT_LENGTH` | 输入字符上限，默认 1000 |
| `REQUESTS_PER_MINUTE` | 每用户分钟限流 |
| `LOG_LEVEL` | 正式环境日志级别 |

真实 `.env` 只存在服务器，不进入 Git。仓库中的 `server-env.example` 只能保留变量名、用途和示例占位符。

### 11.6 BFF 连接 Dify

在当前 Docker 结构下，优先让 BFF 容器通过 Docker 的宿主机网关访问 Dify Nginx，例如将 `DIFY_API_BASE` 指向宿主机网关对应的 `/v1`。不要在文档或源码中写死容器名 `docker-api-1`，因为重新创建 Compose 项目后容器名可能改变。

部署时按以下顺序验证：

1. 在服务器本机确认 Dify `/v1/parameters` 未携带 Key 时返回未授权，说明路径存在且鉴权生效。
2. 从 BFF 容器内确认能访问 Dify 内部地址。
3. 使用测试 Key调用一次配置接口，不在终端历史和日志中打印 Key。
4. 通过 BFF `/healthz` 检查自身进程。
5. 通过 BFF 测试接口完成一次非敏感阻塞请求。
6. 最后测试流式对话、停止生成和删除会话。

BFF 不把 Dify `/parameters` 原样返回前端，只提取开场白、推荐问题和功能开关等白名单字段。Dify 的数据集 ID、节点输入输出、模型用量明细和内部错误只进入脱敏后的服务端观测。

### 11.7 Cloudflare Tunnel 操作流程

推荐使用 Cloudflare 控制台管理 Tunnel：

1. 在 Cloudflare 中创建名为 `shenwang-bff` 的 Tunnel。
2. 根据 Alibaba Cloud Linux 对应的安装方式，在服务器安装 `cloudflared`。
3. 使用 Cloudflare 给出的 Tunnel Token 安装服务；Token 只输入服务器，不写 Git 和群聊。
4. 在 Tunnel 路由中添加 Published Application：`api.example.com` → `http://localhost:3000`。
5. 确认 Tunnel 状态为 Healthy。
6. 从外部网络访问 `https://api.example.com/healthz`，只应看到简单健康响应。
7. 确认 Dify 管理地址、服务器 80 端口和 BFF 3000 端口都没有被安全组额外开放。
8. 配置 Cloudflare 基础速率规则和请求体限制，但业务限流仍以 BFF 为准。

`cloudflared` 应作为系统服务开机启动。它停止时只会导致公网 API 不可用，不应影响服务器内 Dify 自身运行。运维检查分别观察 BFF 容器状态、`cloudflared` 服务状态和 Dify 容器状态，避免把三个层次混为一个问题。

### 11.8 CORS、Cookie 与来源校验

由于 `app.example.com` 和 `api.example.com` 是不同 Origin，浏览器请求需要 CORS，但它们共享同一个根域名，适合使用安全 Cookie。

BFF 必须：

- 只返回精确的 `Access-Control-Allow-Origin: https://app.example.com`，禁止 `*`。
- 只允许实际需要的 GET、POST、DELETE 和 OPTIONS。
- 允许凭据请求，并处理 OPTIONS 预检。
- 对所有写操作检查 `Origin`，不是只相信 CORS。
- Cookie 使用 `HttpOnly`、`Secure`、`SameSite=Lax`，并设置较短有效期。
- 前端请求显式启用 `credentials: include`。
- 不把会话令牌写入 `localStorage` 或 URL。

正式前端和 API 最好使用同一根域名。如果前端长期使用默认 `*.vercel.app` 地址，而 API 使用自有域名，它们会成为跨站点请求，Cookie 和 CSRF 策略将更复杂。因此 `app.example.com` 不只是品牌需求，也是降低鉴权复杂度的技术要求。

### 11.9 SSE 流式链路

流式链路不经过 Vercel Function，而是浏览器直接请求阿里云 BFF：

`浏览器 → Cloudflare Tunnel → Hono BFF → Dify`。

实现要求：

- 前端使用 `fetch` 发送 POST，并读取 `ReadableStream`。
- BFF 收到 Dify 数据块后立即转换并转发，不等待完整回答。
- 响应使用 `text/event-stream`、禁用缓存，并避免代理缓冲和压缩聚合数据块。
- BFF 定期发送保活事件；前端忽略保活但更新连接状态。
- 用户停止后，BFF 调用 Dify stop 接口并主动关闭当前流。
- 浏览器断开时，BFF 取消上游请求，避免模型任务继续消耗费用。
- Cloudflare Tunnel、校园网和手机网络都必须进行首包延迟和中途断流测试。

### 11.10 前端发布流程

前端日常发布不需要 SSH：

1. 开发者从 `main` 创建功能分支。
2. 在本地使用 Mock 或测试 BFF 开发。
3. 推送分支并创建 PR。
4. Vercel 自动生成 Preview URL，产品和前端共同验收。
5. 自动测试通过后由仓库负责人合并到 `main`。
6. Vercel 自动产生 Production 部署并绑定 `app.example.com`。
7. 上线后执行首页、发消息、停止生成和清除会话四项冒烟测试。

生产回滚优先使用 Vercel 的历史部署恢复，不通过紧急修改 `main` 伪造回滚。回滚后再在 Git 中补充正确的修复提交，保持仓库与线上状态可解释。

### 11.11 BFF 发布流程

BFF 与前端独立发布，不能因为前端样式修改而自动重启服务器服务：

1. `worker/` 的修改通过 PR 评审，重点检查密钥、日志和接口兼容性。
2. 合并后创建明确版本号或记录提交 SHA。
3. 服务器负责人通过 SSH 登录，在项目目录拉取指定提交。
4. 构建带提交 SHA 标签的 BFF 镜像。
5. 更新 Compose 使用的新镜像并后台启动。
6. 依次检查容器状态、`/healthz`、Dify 连通和一条流式测试。
7. 观察错误率和日志后再宣布发布完成。

如新版本失败，切回上一个镜像标签并重新启动 BFF；不要回滚或重建 Dify。Dify Key 轮换时，先创建新 Key、更新服务器环境并验证，再删除旧 Key，避免服务中断。

### 11.12 本地开发与真实联调

前端开发分两种模式：

- Mock 模式：本地 Vite 使用模拟 SSE，不需要 SSH、不需要 Dify Key，适合绝大多数界面开发。
- 联调模式：本地前端调用测试 BFF；只有 BFF/Dify 负责人需要管理服务器和 Key。

若需要在本机直接调试 BFF，可以通过现有 SSH 配置增加一个仅本机可见的端口转发，把服务器 Dify `/v1` 转到本地 BFF。不得为了方便联调把 Dify Key分发给所有前端开发者。

### 11.13 运维边界

| 故障表现 | 优先检查 |
| --- | --- |
| Vercel 页面打不开 | Vercel Deployment、域名 DNS |
| 页面能开但 API 全部失败 | Tunnel 状态、BFF `/healthz`、CORS |
| API 可连接但 AI 不回答 | BFF 到 Dify 网络、Dify Key、Dify 容器 |
| 能回答但没有流式效果 | BFF 转发、响应头、代理缓冲、网络环境 |
| 只有某类问题失败 | Dify 路由、模型节点、知识库绑定 |
| 服务器重启后 API 失败 | Docker 自动启动、BFF restart、cloudflared 服务 |

当前服务器使用外部模型 API，React 静态资源由 Vercel 承担，阿里云新增的主要负担只有轻量 BFF 和现有 Dify 流式连接。主要监控指标应包括请求量、并发数、首字响应时间、完整回答时间、上游失败率、Dify 路由类别和模型用量，不记录完整儿童问答。

## 12. 开发与联调顺序

### 阶段 A：界面骨架和 Mock

1. 创建 `web/` React + TypeScript 工程。
2. 完成移动端聊天布局、隐私提示和三类快捷入口。
3. 使用本地 Mock SSE 模拟 `status`、`delta`、`done` 和 `error`。
4. 完成状态机、停止按钮和错误界面。

验收：不连接 Dify 也能完整演示一次流式对话和所有异常状态。

### 阶段 B：BFF 与 Dify

1. 创建 `worker/` Hono 工程。
2. 接入 `POST /chat-messages` 流式接口。
3. 转换 SSE 事件并隐藏内部节点信息。
4. 接入停止生成和删除会话。
5. 加入访问控制、限流、输入校验和脱敏日志。

验收：API Key 不出现在浏览器网络响应和前端构建文件中。

### 阶段 C：六类业务联调

分别验证：

1. 学习问题命中学习知识库。
2. 中心问题只引用中心资料。
3. 普通问候不访问知识库。
4. 非紧急情绪问题提供温和支持，不诊断。
5. 高风险问题只走固定回复。
6. 超出能力的问题明确拒答。

验收：每一类至少准备 5 条正常案例和 3 条边界案例，并在 Dify 日志中确认路由正确。

### 阶段 D：部署与小范围试点

1. 将根域名接入 Cloudflare，确定 `app` 和 `api` 两个子域名。
2. 在阿里云部署只监听 `127.0.0.1:3000` 的 BFF。
3. 创建 Cloudflare Tunnel，将 `api` 子域名映射到 BFF。
4. 连接 GitHub 与 Netlify，将 Base directory 设为 `web`、Publish directory 设为 `dist`，并配置 Production 环境。
5. 为 `app` 子域名配置 Netlify 自定义域名。
6. 配置精确 CORS、试点访问码、Cookie、限流和健康检查。
7. 验证 Netlify Deploy Preview 不会默认访问正式 BFF。
8. 使用真实手机测试校园网、移动网络、弱网和 SSE 中途断流。
9. 完成教师/专业人员内容审核后再邀请儿童使用。

## 13. 测试清单

### 功能

- 首次发送获得 `conversationId`，后续发送复用该 ID。
- 快速连续点击不会产生重复消息。
- 停止按钮能终止当前任务。
- 新对话不会携带旧会话上下文。
- 清除对话同时清除 Dify 会话和浏览器 ID。
- `message_replace` 能正确替换已显示内容。
- Markdown 列表、表格和代码不会破坏页面。

### 异常

- SSH / 上游断开时显示服务不可用。
- Cloudflare Tunnel 停止时显示服务不可用，Dify 后台仍可由管理员通过 SSH 访问。
- 首包超时和中途断流有不同提示。
- 429 不自动无限重试。
- 页面刷新、切换网络和重复发送不会卡死输入框。
- BFF 重启后前端能够恢复到可继续操作状态。
- Vercel 前端回滚后仍能兼容当前 BFF 接口版本。

### 安全与隐私

- 在前端源码、构建产物和浏览器存储中搜索不到任何 API Key。
- HTML、脚本和恶意 Markdown 不会执行。
- 超长输入、空输入和异常 JSON 被拒绝。
- 日志中没有完整儿童问答和身份信息。
- 高风险案例不进入普通模型自由回答分支。
- 正式 BFF 只允许精确的 `app` 域名，不允许任意 Vercel Preview 来源。
- 直接访问服务器公网 IP、3000 端口或 Dify API 均不能绕过 Tunnel/BFF。
- Vercel 环境变量中不存在 Dify Key、访问码原文和服务器凭据。

### 可用性

- 360px、390px、430px 手机宽度正常。
- 桌面端最大阅读宽度合理。
- 只用键盘可以发送、停止和新建对话。
- 屏幕阅读器能获知“正在回答”和“回答完成”。
- 弱网下已生成的文字不会丢失。

9. 在线版本发布后，谁负责导出 DSL 并提交到仓库。
10. 谁负责维护 Tunnel Token、BFF 环境变量和 Key 轮换记录。

1. `web: 初始化 React + TypeScript + Vite`。
